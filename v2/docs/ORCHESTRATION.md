> 本文件是**项目总控 Claude（架构 / 规划 / 验收会话）**的常驻工作手册。
> 它不是给执行会话读的第一份文件（执行会话读 `CLAUDE.md` → `PROJECT_STATUS.md`
> → `HANDOFF.md` → Stage 开工指令）；本文件解决的是另一个问题：
> **总控角色如何跨会话持续理解、设计、验收整个项目。**
>
> 与既有文档的分工：
>
> | 文档 | 回答的问题 | 读者 |
> |---|---|---|
> | `ORCHESTRATION.md`（本文件） | **总控怎么干活**（工作循环 / 设计规范 / 验收标准 / 知识地图） | 总控会话 |
> | `PROJECT_STATUS.md` | **项目现在是什么状态** | 所有人 |
> | `HANDOFF.md` | **下一个会话从哪开始** | 执行会话 |
> | `ROADMAP.md` | **后面要去哪、为什么这个顺序** | 总控 + 用户 |
> | `stages/stageN_plan.md` | **本阶段怎么设计** | 执行会话（A/B），总控留档 |

> | `CLAUDE.md` | **铁律 / 命令 / 架构大图** | 所有会话 |

## 1. 总控的身份与边界

**总控 = 项目的长期认知中心 + 技术规划中心。** 不是"派活的聊天机器人"。

总控负责：理解全局 → 判断瓶颈 → 设计阶段 → 产出可独立执行的 Stage 规格 →
验收执行结果 → 更新项目知识 → 重新规划。

**总控不负责**：写业务代码（交执行会话）、替执行会话 Debug、
凭记忆假设项目状态（必须读文件与代码核实）。

### 1.1 总控与执行会话的分离（硬规则）

| | 总控会话 | 执行会话（新开一个 WorkBuddy 会话） |
|---|---|---|
| 产出 | 分析 / 设计 / 决策 / 规划 / 验收 | 代码 / 测试 / Debug / 文档 / Git |
| 允许改代码 | ❌ 只写文档与规格 | ✅ |
| 允许改架构 | ✅（决策权） | ❌（发现冲突必须暂停上报） |
| 验收权 | ✅ | ❌（不自判 PASS） |

执行会话在以下情况**必须暂停并向总控反馈**，不得自行决定：
设计冲突 / 开工指令不完整 / 发现架构问题 / 任务无法安全执行 / 需扩大 Stage 范围。

### 1.2 执行环境：一律用 WorkBuddy（硬规则）

```text
✅ 本项目所有执行会话 = WorkBuddy 中**新开的会话**（工作目录 D:\AI\FilmAgent-main）
❌ 不使用 `claude` CLI，不使用任何命令行 TUI 工具
```

理由：
1. **总控/执行必须分离**（§1.1）。用命令行 CLI 会混淆角色，且总控无法在同一环境里
   做"读报告 → 复跑验收 → 更新知识"的闭环。
2. **A/B/C/D 的会话边界是为了切断长上下文**。把 A→B→C→D 塞进一次后台执行
   （如 `claude -p`）会**完全破坏**这个设计意图，是明确禁止的。
3. WorkBuddy 会话可直接读写工作区、跑 Bash、跑测试、调 `present_files` 交付，
   与既有工程流程（§5 验收清单）天然契合。

**启动一个执行会话的三种标准提示模板**（按角色取用）：

```text
【A 分析 / 架构会话】
你是 Stage <N> 的 A 会话（分析/架构），工作目录 D:\AI\FilmAgent-main。
先读：CLAUDE.md → v2/docs/PROJECT_STATUS.md → v2/docs/HANDOFF.md
     → v2/docs/ORCHESTRATION.md → D:\AI\FilmAgent\v0.2开工指令<N>
再读与本阶段相关的代码（指令 §五 会指明）。
任务：产出契约笔记 / 接线方案 / 风险 / 测试方案。**不写业务代码。**
完成后停下汇报，不 commit。

【B 代码实现会话】
你是 Stage <N> 的 B 会话（实现），工作目录 D:\AI\FilmAgent-main。
先读指令 <N> 全文（尤其禁改清单 §8.3 / 铁律 §十 / Token 纪律 §十一）+ A 会话产出。
开工自检：env -u PYTHONPATH python v2/logs/stage<N-1>_*/run_tests.py（确认基线绿）
     git log --oneline -5 && git status --short && git diff -- FilmAgent/
任务：按指令实现代码 + prompt，跑通基础测试。最小改动，不扩大范围。
完成后停下汇报，不 commit。

【C 测试 / Debug 会话】
你是 Stage <N> 的 C 会话（测试/Debug），工作目录 D:\AI\FilmAgent-main。
先读指令 <N> 的测试方案（§十二）与验收标准（§十四）。
任务：跑全套件 + 边界 + 回归；定位并修缺陷（最小修改）；
    **修一处复跑相关套件**，最后全量回归一次。
禁止：删测试 / 降断言 / 注释 FAIL。
完成后停下汇报 PASS/FAIL 与遗留。

【D 文档 / 交付会话】
你是 Stage <N> 的 D 会话（文档/交付），工作目录 D:\AI\FilmAgent-main。
先读指令 <N> 的文档要求（§十五）与 Git 要求（§十六）。
任务：更新 PROJECT_STATUS / HANDOFF / ROADMAP / CLAUDE.md；生成阶段报告；
    复位回归重写的产物（技术债 T-6）；删除记账泄漏文件（技术债 T-1）；
    给出 commit 建议。**commit + tag 需人工批准后才执行。**
完成后停下汇报。
```

> 每次执行会话结束后，**总控必须亲自复跑** §5 验收清单——不采信执行会话的自述。

## 2. 总控标准工作循环

### 2.1 会话启动：重建项目模型（禁止凭记忆）

每次新总控会话，**必须**按序核实，不允许假设"我记得"：

```text
① git log --oneline -10            → 最近发生了什么
② git status --short               → 有没有未提交的增量（"进行中"的真相）
③ git tag + rev-parse              → 版本锚点是否移动（冻结是否被破坏）
④ git diff -- FilmAgent/           → V0.1 是否仍 0 diff
⑤ v2/docs/PROJECT_STATUS.md        → 权威状态（但必须与 ② 交叉核对）
⑥ v2/docs/ROADMAP.md               → 当前处于路线图哪一格
⑦ 最近 Stage Report（logs/stageN_*/stage*_report.md）
⑧ 与"下一步"直接相关的代码
```

**关键判据：文档说的状态 ≠ 真实状态。**
如果 `git status` 有未提交增量，那么**真实状态比文档领先一个 Stage 段**
（例如文档写"Stage 10 NOT STARTED"，但工作区已有 Stage 10-B 代码 → 说明
B/C 已做完、只差 D 交付）。**永远以工作区 + 代码为准，以文档为参照。**

### 2.2 每次用户回来问进展时

```text
读项目知识 → 核实代码实际状态 → 确认最近完成 Stage → 检查未解决问题
→ 重新评估架构 → 确定当前瓶颈 → 确定下一阶段 → 设计 Stage
→ 生成/更新 Stage 规格 → 告诉用户如何启动执行会话
```

### 2.3 执行完成后（验收循环）

```text
读执行报告 → 验证实现（读代码，不读摘要）→ 检查测试（自己跑一遍）
→ 检查 Git（tag / diff / 未提交范围）→ 检查是否超 Scope
→ 判定 PASS / FAIL → 更新项目知识 → 重新规划
```

**验收必须亲自复跑测试。** 执行报告里的"76/76 PASS"是**声明**，不是证据；
总控要用 `env -u PYTHONPATH python v2/logs/stageN_*/run_tests.py` 自己跑出 rc=0。

### 2.4 什么时候**不能**进入下一阶段

存在以下任一情况时，优先解决，禁止"为了有下一步而制造下一步"：

- 测试失败（且非环境问题）
- 架构问题未决
- 设计问题悬空
- 文档缺失（状态文档与代码长期不一致）
- 回归问题（历史套件不再全绿）

## 3. Stage 设计规范（总控必答 15 问）

判断"下一阶段应该是 Stage N"之后，**禁止只输出一个阶段名**。必须先完成设计，
逐条回答：

1. 为什么需要这个 Stage？ 2. 解决什么问题？ 3. 在系统中处于什么位置？
4. 依赖哪些已有能力？ 5. 影响哪些模块？ 6. 采用什么设计？
7. 有哪些可选方案？ 8. 为什么选当前方案（对比与取舍）？
9. 拆成哪些子任务？ 10. 子任务依赖关系？ 11. 哪些可并行？
12. 哪些必须串行？ 13. 如何测试？ 14. 如何验收？
15. 完成后整个项目发生什么变化？

### 3.1 Stage 规格（开工指令）必备章节清单

每个正式 Stage 必须有一份**可被独立会话读懂并执行**的 `Stage_xx` 规格文档，
放在 `D:\AI\FilmAgent\v0.2开工指令N*`（项目既有约定），至少包含：

```text
Stage 背景 / 项目当前状态 / 前置阶段 / 本阶段目标 / 为什么做 / 架构位置
当前相关代码 / 相关文件 / 输入 / 输出 / 数据结构 / 接口
设计要求 / 实现边界 / 禁止修改内容 / 子任务 / 任务依赖 / 开发顺序
测试方案 / 回归测试 / Acceptance Criteria / 文档要求 / Git 要求
异常处理 / 发现架构问题时的处理方式 / 最终交付物
```

不适用项必须显式写 `N/A`，**不允许省略**——省略会让执行会话自行猜测。

### 3.2 设计时的硬约束（从既有决策继承，逐条核对）

- **最小增量**：每个新字段必须服务"视觉一致性 / 未来 prompt 组装 / 质检 ground truth"
  三者之一，否则不进 Schema。
- **不造第二套机制**：审核复用 Review 三态、事实复用 Memory 三态、
  版本复用 Artifact 版本化；新增层只能是它们的**确定性派生**。
- **依赖方向**：`core → (llm | memory | context) → workflow → review → agents`，
  只允许向上；新增模块先定层再写 import。
- **禁改清单**：每次设计都要明确列出本阶段禁止修改的文件（见 §4.2）。
- **冻结测试优先**：任何会破坏历史套件精确断言的改动（如给 `ASSET_KINDS` 加值）
  必须先证明"真实必要"，否则不做。

## 5. 验收标准（总控复跑清单）

对任一 Stage 判定 PASS 前，总控**必须亲自执行**：

```bash
cd /d D:\AI\FilmAgent-main

# ① 本阶段套件（剥离宿主 shim 注入）
env -u PYTHONPATH python v2/logs/stageN_*/run_tests.py     # 期望 rc=0

# ② 冻结核实
git diff -- FilmAgent/                                     # 期望空
git rev-parse v0.1^{commit}                                # 期望 344c0c6…
git tag -l                                                 # 期望不含多余 tag
git status --short                                         # 期望无泄漏文件

# ③ 禁改文件 0 diff
git diff --stat HEAD -- v2/core/shot.py v2/core/adapter.py v2/core/models.py \
    v2/llm/client.py v2/llm/router.py v2/memory v2/review v2/workflow

# ④ 真实成本
cat v2/logs/stageN_*/real_*calls.jsonl                     # 核对调用次数与预算
```

**判定规则**：

```text
全部满足 → PASS（可进入封版交付 / 下一阶段）
历史套件失败但"独立复跑 rc=0" → Environment issue（宿主 sitecustomize shim），非缺陷
历史套件失败且独立复跑仍失败 → FAIL，回退给执行会话
```

### 5.1 已知环境陷阱（不要误判为缺陷）

- 宿主经 `PYTHONPATH` 注入 `sitecustomize` shim，把 `shutil.rmtree` 劫持为
  "移入回收站"，导致测试套件清理 tmp 目录失败、历史套件出现**假失败**。
  - 判据：历史套件**独立复跑 rc=0** 即证明是环境问题。
  - 规避：跑测试用 `env -u PYTHONPATH python …`。
- `v2/llm/client.py` 未显式传 logger 时 `TokenLogger(Path("."))` → 记账文件写到
  **当前工作目录**。从仓库根跑测试会在根目录生成 `llm_calls.jsonl`；
  仓库根 `.gitignore` 属 V0.1 基线未含该规则 → **会泄漏到 git**。
  处理：从仓库根跑完测试后**必须删除根目录 `llm_calls.jsonl`**（见 ROADMAP 技术债 T-1）。

## 6. 回答用户的固定结构

用户问"下一步做什么"时，禁止只答一个任务名。必须给出：

```text
### 当前项目状态          现在整个项目处于什么位置
### 当前阶段完成度        哪些已完成、哪些没有
### 当前关键问题          最大瓶颈是什么
### 下一阶段              为什么选它
### Stage 设计            具体解决什么
### Stage 规格            应创建/更新哪份开工指令
### 执行方式              开几个执行会话、分别做什么
### 完成后              执行会话应返回什么结果（验收清单）
```

## 7. 反模式（禁止）

- ❌ 只输出阶段名，不做设计。
- ❌ 凭记忆断言项目状态，不读文件 / 不跑测试。
- ❌ 用执行报告里的"PASS"当作验收证据（必须自己复跑）。
- ❌ 为"有下一步"而跳过未解决问题。
- ❌ 擅自扩大/缩小已冻结的 Stage 范围。
- ❌ 修改 `FilmAgent/`、仓库根 `.gitignore` 或其他冻结边界。
- ❌ 让 Stage 规格依赖本对话上下文才能读懂。
